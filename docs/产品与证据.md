# 流向 · 产品与证据

当前说明对应 0.6.0；通用功能和实现状态见 [需求核查与待办](需求核查与待办.md)，具体软件和故障来源见 [应用实例与验收案例](应用实例与验收案例.md)。2026-11-08 先将功能与实例分开，再将已有应用检查、诊断、预览、应用与验证串成共享流程；尚未实现的能力不因重构而宣称完成。

把本机的应用、规则与出口画成可解释的连接图。调音台提供通道与状态，节点软件提供连接与属性，应用通道提供可复制的独立代理入口。

## 面向问题类型的产品组织

产品按软件发现、配置溯源、连接策略、设置应用、诊断、日志关联、健康观察、请求分析与配置迁移等可复用能力组织需求。当前画布以软件为起点，提供检查、诊断、应用、验证四步；连接设置、进程环境、工作台目标探测与原软件结果分别呈现。日志关联、持续健康观察、请求分析和迁移仍有独立缺口。软件名字用于选择对象，不用于划分产品功能模块。

例如，“模型后台不采用代理”和“启动器将旧变量传给游戏”都涉及配置作用范围、进程关系与应用生命周期；“安装无进展”和“后台稍后掉线”都需要日志/活动证据和健康判断。各自的差异成为适配输入和验收案例，共用功能负责组织证据与下一步。

实现按以下职责分离。0.6.0 已引入内置应用适配接口与共享编排；没有用户可执行插件框架，也没有为未知后台自动生成生命周期命令：

| 职责 | 负责什么 | 边界 |
| --- | --- | --- |
| 通用操作与界面 | 软件选择、连接意图、状态解释、预览、应用、复测、恢复及快捷入口 | 不为每个软件复制整套向导；每次动作显示实际支持范围 |
| 通用证据与判断 | 来源、时间、身份、有效期、进程关系、失败层级、可能原因与缺失信息 | 单个端口、环境变量或历史案例不能直接决定全部路径与根因 |
| 平台与软件能力适配 | Windows 配置层、协议/引擎能力、软件路径/日志格式、健康与生命周期接口 | 只提供差异数据、检查和受支持动作；不得绕过共享保护、擅自重启或自称业务成功 |
| 应用实例与验收 | 具体环境、操作、结果、反例、复用覆盖 | 不把案例升级成另一套功能模块；一个实例通过不关闭整个通用需求 |

未知软件应能登记、查看通用证据并补充信息；没有适配时显示不支持或待确认，不凭名称猜测。适配仍然必要：不同程序的配置与安全重启方式确有差异；通用化不意味着删掉这些保护，也不意味着所有协议和软件立刻可控。

`app_adapters.py` 提供普通进程环境、浏览器显式参数及已适配后台的能力与差异；`app_connections.py` 统一承担检查、预览票据、状态复核与执行后验证。Hermes 生命周期和安装身份仍由 `hermes_adapter.py` 提供，原任务、身份及旧窗口保护保留。第二种合成后台适配和未知应用测试用于证明机制复用，不宣称新增了真实软件支持。

`app_workflow.py` 与 `service.py` 复用现有检查及 HEAD 探测组织诊断和验证。地址可留空；有地址时，诊断比较候选路径，验证只检查已保存路径。建议只改变连线草稿，执行必须先保存和预览。保存或应用使旧验证记录失效，应用进行中不能发布验证或提交反馈；失败操作也会使旧证据失效。用户确认恢复或仍失败独立标为用户反馈，不提升为自动业务证明。

日志发现仍由 `catalog.py` 的已知和通用候选路径实现；完整进程关系、日志时间线、健康观察与请求分析没有在本轮扩展。只新增几个目录、一个重启命令或一条报错匹配，不应作为这些通用能力的交付。

## 开发与验收约束

每次新增功能先说明它解决的问题类型、复用现有哪项能力、适配差异在哪里，再给正常、失败、未知和反例。具体适配的完成与通用功能的完成分别记录；通用能力要有不同结构的样例支持。功能选择不等于选定供应商：“请求/会话分析”是需求，Fiddler 是参照；逐应用接管引擎的选择仍需单独评估。

“逐应用流量接管可扩展”“内核出口关联”“日志本次写入”仍是目标或证据要求；当前尚未全部实现。F07 持续观察、F08 请求分析等原先完全未实现的能力本轮暂缓开发。已有隔离测试和历史软件修复不能替代这些功能的验收。

## 工作方式

1. 检测：读取系统代理/PAC、WinHTTP、环境变量、监听端口、进程归属、网络接口/路由/DNS/hosts。
2. 接线：每个通道的默认出口与有序域名规则可调整，预览匹配结果。
3. 运行：在环回地址启动本工具的 HTTP/CONNECT/SOCKS5 TCP 入口；仅处理实际送到这些入口的连接，不做 HTTPS 解密。
4. 接入：应用自身支持代理时填入专属端口。系统代理接入需明确应用并可回退；忽略这些设置的应用仍需其支持的独立接入方式。
5. 验证：记录 DNS、连接、TLS/HTTP 和中继事件。未知状态不会被涂成通过。

## 不做隐式动作

不重启 Codex/代理核心，不改 TUN 或默认路由，不导入节点密钥，不自动更换订阅；不强行给任意进程注入网络钩子。普通 TCP 直连仍可能经过 TUN。SOCKS UDP、QUIC 和真实 RustDesk 会话不因 TCP 检查通过就被认定成功。

## 本轮设计修正（2026-10-24）

补入的需求是以软件为单位直观看到“在哪里设置代理、可以采用哪种控制方式、当前连接有什么证据、日志在哪里”。产品同时呈现 Windows 各层代理来源、应用接入方式与运行事实；现有 TCP 接线能力作为一种接入方式保留，逐应用流量接管可通过成熟引擎适配扩展。

本轮已找到 ProxyBridge、ProxiFyre、Proxifier 等能够处理逐应用路由与连接观察的工具，但未找到同时覆盖全部配置层、软件配置与证据定位的完整工具。调查范围、推荐定位、TCP/UDP 边界和精确官方来源见 [Windows 代理工具调查](工具调查-20261024.txt)。

设计要求是分别标注配置值、控制应用结果、观察到的连接、内核出口关联与目标应用实测。当前已有设置来源、启动/应用结果、TCP 下一跳和本工具中继事件；第三方内核的最终出口关联、真实业务自动验证尚未实现。工作台自己的探测不能代替目标软件的实际路径证据。日志已区分候选路径与本机存在的资源，但尚未持续观察写入，不能标成“本次故障已写入的日志”。
