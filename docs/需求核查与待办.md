# 通用功能需求、实现核查与待办

更新：2026-11-08（Asia/Singapore）。当前核查为 **0.6.0**，从 0.5.1 / Git `309f962` 演进。先完成需求与实例分离，再实现已有能力的共享检查、诊断、预览应用与验证；下方保留旧版验收记录。

本文件按**要解决的问题类型和可复用功能**组织。具体软件、机器、报错和操作经历另见 [应用实例与验收案例](应用实例与验收案例.md)。案例为功能提供来源和验证，不独立演变为一组软件专用修复按钮。

面向所有用户，意味着同类问题采用同一套操作与判断方式；不意味着未经验证就宣称支持所有软件。支持范围由可观察证据和接入能力决定，未知软件也应能进入通用流程，并明确显示哪些能力可用、哪些信息不足。

## 需求组织与完成原则

- 每项功能记录：用户目标、适用对象、通用行为、当前实现、缺口和完成标准；功能标题不以某个软件名或某次报错命名。
- 每个实例记录：现象、环境、证据、假设、涉及的功能、应用结果和反例。一次修复成功不能代替通用功能验收，也不能成为其他机器的默认诊断结论。
- 软件差异通过能力适配处理：提供识别、配置/日志位置、健康检查、启动/停止等必要接口。检查、解释、影响预览、应用、验证和恢复由共享流程负责。
- 新问题先判断是已有能力的缺陷、缺少一种适配，还是确有新的通用能力需求；不按软件名复制整套流程，也不预先建设没有案例支撑的万能框架。
- 已有特定软件适配属于实现证据，不能单独证明通用能力完成。本轮抽取共享逻辑保留原行为和保护措施，以未知普通应用、浏览器及第二种合成后台适配验证机制复用；合成适配不代表新增真实软件支持。

状态：**已有基础 / 部分实现 / 未实现**描述能力范围；**待验证**描述证据不足，两者分别记录。以下为产品需求与验收标准，未完成项不代表已排期；具体引擎、数据结构、证书方案和自动恢复策略尚未选定。

本轮范围限于已有能力的通用化与流程贯通。F07 持续观察/停滞诊断、F08 请求分析，以及原来完全未实现的逐进程接管、日志时间线、跨机自动迁移等不在本轮开发范围；不将这些待办标为完成。

## 功能需求与当前实现

### F01 · 软件、网络工具与接入能力发现

**用户目标：** 找到本机软件及可用连接方式，不必手查端口，也不会把加速器或组网管理端口误当代理。

**通用行为：** 综合安装记录、进程、服务、接口、配置引用及监听建立软件清单；提供手动补充。区分“已安装、运行中、有监听、协议声明、协议实测、目标可达”。网络工具按能力提供连接或观察，不按品牌统一赋予 HTTP 能力；端口变化和陈旧信息可重新核对。

**现状：部分实现。** 添加软件、已知工具识别、显示/拖入、有限配置解析和本机 HTTP CONNECT 检测已有；0.6.0 增加内置应用能力声明，区分普通环境、浏览器显式参数、已适配后台及不支持对象。未知软件/自定义布局自动识别、网络工具能力与失效信息更新仍不完整；后台不会因通用接口存在就自动得到支持。协议确认仅保存在当前服务内。依据：`app_adapters.py`、`discovery.py`、`network_tools.py`、`proxy_check.py`、`catalog.py`，`web/app.js` 的 `appFlowShowTool` / `appFlowToolDrop`。

**完成标准：** 同一流程覆盖有 HTTP、纯 SOCKS、无监听、专用隧道及未知软件；端口/所属进程变化后不沿用旧确认；用户能补充缺失信息，不依赖预置的某一端口。

### F02 · 配置来源、作用范围与进程继承关系

**用户目标：** 知道哪个设置影响哪个进程，为什么“系统代理已关”或“变量已删”仍与实际表现不一致。

**通用行为：** 分开展示 WinINet/PAC、WinHTTP、用户/机器持久环境、运行进程环境、应用私有配置及路由层；追踪主程序、启动器、子进程、独立后台的关系与来源可信度。对支持修改的层提供明确范围、原值、新值、刷新条件和恢复方式；不支持的层明确只读。进程关系不是继承已生效的充分证据。

**现状：部分实现。** 分层快照、按需代理变量白名单读取、新进程环境和受控 WinINet 接入已有；0.6.0 通过能力适配提供后台身份、窗口环境、活动任务与支持范围，并由共享检查输出证据。真实后台识别仍只覆盖已有 Hermes 适配，缺任意软件进程关系视图、广泛后台发现、统一配置冲突解释和多层编辑器。依据：`app_adapters.py`、`app_connections.py`、`discovery.py`、`process_proxy.py`、`catalog.py` 的 `_settings`、`proxy_environment.py`、`system_proxy.py`。

**完成标准：** 区分持久值与活进程值、同名程序的不同实例、启动器与后台；对“有残留变量”和“没有变量但仍失败”给出不同结论。任何修改都说明影响对象，不把清除子进程环境称为全局直连。

### F03 · 可视化连接策略与适合软件的接入方式

**用户目标：** 在画布中表达软件或不同目标的连接方式，并知道该软件能否实际采用。

**通用行为：** 用具体目标、匹配范围、顺序和默认去向表达规则；按软件能力选择环境、显式参数、私有配置、本地中继或受支持的逐进程引擎。协议、身份认证、DNS、TCP/UDP/QUIC、TUN 的支持范围分别说明；不支持时提供有依据的下一步，不把连线当作控制成功。

**现状：部分实现。** 应用画布、具体域名与状态分层、TCP 中继已有。默认应用连接限本机无认证 HTTP；中继支持 SOCKS5 TCP 上游；脚本 SOCKS 环境仅开放给 curl/Git。没有通用强制接管、UDP/QUIC 或强制绕过 TUN。依据：`app_routes.py`、`app_launch.py`、`relay.py`、`policy.py`、`web/routing-view.js`。

**完成标准：** 同一策略在不同接入方式下明确说明能力和效果；支持代理与忽略代理的样例不能得出同样的成功结论。测试验证真实请求的匹配结果，未匹配规则和不可用协议有可解释结果。

### F04 · 设置应用、进程生命周期与快捷复用

**用户目标：** 保存一次后方便复用；有旧实例、子进程或后台时，清楚知道需要刷新什么。

**通用行为：** 共享“检查当前对象 → 预览影响 → 应用 → 读回验证 → 必要时恢复”流程，桌面快捷方式与 GUI 使用一致的设置和检查。软件适配提供受支持的生命周期操作及任务保护，核心流程不写死某个软件的重启逻辑。未知身份、状态变化或无法安全恢复时报告原因，不盲目操作。

**现状：已有共享机制，功能范围仍部分实现。** 0.6.0 将普通应用与已适配后台放入同一检查、预览、执行和执行后校验机制；后台差异由内置适配提供，核心不按软件名决定重启。GUI 中所有应用都须先取得一次性预览票据；设置、进程或后台状态变化会拒绝旧票据。快捷方式复用共享计划和执行检查，后台任务、身份和旧窗口保护保留。未知软件仍采用普通新进程方式；尚无任意后台控制或通用恢复操作，快捷方式代理预检仅为 TCP 可达。依据：`app_adapters.py`、`app_connections.py`、`app_launch.py`、`app_shortcuts.py`、`tests/test_app_adapters.py`。

**完成标准：** 普通应用、带启动器应用、独立后台应用走同一流程；进行中任务、旧窗口、身份变化、超时及部分失败有明确结果。GUI 和快捷方式不绕过彼此的保护；恢复能力按实际操作声明，不承诺不可逆操作可以无损撤销。

### F05 · 基于证据的故障诊断与处理流程

**用户目标：** 从“这个软件连不上/很慢”开始，按清晰步骤获得原因证据、可执行建议和复测结果。

**通用行为：** 在画布中选故障对象，补充操作/地址/错误 → 收集相关配置、进程、日志与连接证据 → 在适用范围对比路径 → 区分已确认原因、可能原因和缺失证据 → 预览处理 → 应用 → 在原软件复测。失败后保留结果并指导下一步，同一问题类型不按软件另起一套向导。

**现状：已有画布共享流程，诊断覆盖仍部分实现。** 0.6.0 以检查、诊断、应用、验证四步组织已有进程检查与 HEAD 对照。地址可留空；填写时诊断使用合并后的当前代理入口证据，建议只能放入草稿，保存并预览后才能应用。验证使用已保存设置，用户另行记录“原软件已正常”或“仍然失败”，不会把探测成功等同业务恢复。保存、应用及检查期间状态变化会使旧验证记录失效；应用失败也不会保留旧有效证据。尚无日志自动归因、完整会话验证或持续健康诊断。旧向导仍隐藏，已拒绝直接启动。依据：`app_workflow.py`、`troubleshoot.py`、`service.py` 的 `app_route_workflow` / `app_route_feedback` / `_workflow_tools`、`web/app.js`、`tests/test_app_workflow.py`。

**完成标准：** 同一症状的不同原因能分开；证据不全时停留在“待确认”并给出下一步；工作台探测成功但原软件仍失败必须有后续分支，不能标修复完成。未知软件可使用通用检查，不强行套用已知案例的结论。

### F06 · 日志、连接与事件的统一定位和关联

**用户目标：** 不必猜日志目录，能把某次失败与相关进程、配置变化和连接事件对应起来。

**通用行为：** 支持自动发现与用户登记日志来源，覆盖程序目录、用户数据、服务及子进程来源；区分候选、存在、本次写入和已读取。保留时间、来源、身份、脱敏及轮转信息，关联网络与应用事件；不能关联时明确保留未知。

**现状：部分实现。** 已知/通用候选目录、有限脱敏尾部、TCP 下一跳摘要和中继事件已有；缺自定义来源登记、通用多进程日志关联、持续写入观察和第三方内核最终出口关联。仅新增几个目录不能算本项完成。依据：`catalog.py` 的 `_locations` / `_resource` / `tail`、`discovery.py` 的 `_network_processes`、`relay.py`。

**完成标准：** 换目录、日志轮转、多进程、无日志权限或没有适配时仍有明确操作；不同类型应用通过相同界面查看来源与时间线。不能将旧日志、端口连接或后台存在当作当前业务正常。

### F07 · 慢请求、停滞、掉线与恢复评估

**用户目标：** 分辨仍在工作、网络慢、任务停滞、后台不可用或业务失败，并知道是否适合重试/重启。

**通用行为：** 在选定观察时段联合使用活动进展、连接、日志和健康接口；将下载、计算、等待输入、进程存活、服务就绪和业务成功分别呈现。提供有依据的处理预览与复测；持续监测和自动恢复需有明确范围、停止条件及用户设置，不由一次修复默认开启。

**现状：通用能力未实现，本轮暂缓。** 目前只有点时检查、有限探测及已适配后台的按需操作；没有统一性能/停滞诊断、持续健康观察或故障时间线。`guardian.py` 仅负责本工具系统代理回退，不是任意应用健康守护。四步流程没有新增自动循环检测或重启。

**完成标准：** 同样“长时间无界面进展”在缓慢下载、仍有计算、等待输入及后台退出样例中得到不同解释；连续失败、任务进行中、监控停止及证据不足均有明确边界。自动恢复若交付，单独验收，不能靠循环重启代替诊断。

### F08 · 请求与会话分析

**用户目标：** 查看一次网络操作的请求、响应、耗时和错误，按需要复现问题。Fiddler 是用户提出的能力参照，不是功能边界或已选依赖。

**通用行为：** 提供有来源范围的请求/会话列表、筛选与详情；分别定义明文可见性、HTTPS 解密、正文处理、修改/重放和导入导出的支持范围。说明哪些连接进入观察范围及不能观察的原因；关联应用身份时必须有证据。

**现状：未实现，本轮暂缓。** 无抓包会话列表、请求/响应正文、HTTPS 解密、修改/重放或 HAR 工具。活动、日志尾部与 HEAD 探测不能替代此功能；`relay.py` 明确 `tls_mitm=False`。内置实现还是外部工具适配待设计。

**完成标准：** 多个应用/测试客户端通过同一分析界面展示结果；正文截断、脱敏、加密不可见及协议限制明确。若提供 HTTPS 解密，证书安装/撤销与作用范围须可控制；重放、修改、导入导出逐项验收，不用其中一项代表全套完成。

### F09 · 配置复用、跨机迁移与版本兼容

**用户目标：** 更新或换电脑后保留意图，找到本机实际程序和入口，避免旧端口、绝对路径或适配版本失效。

**通用行为：** 分开保存用户意图与本机绑定，迁移时重新发现并预览绑定；明确导出范围、失效记录、数据版本、升级/恢复路径和运行后台版本。程序打包完整性与配置兼容分别校验，失效时保留原数据。

**现状：部分实现。** 独立 EXE、项目/用户数据目录、构建校验、配置持久化和快捷方式已有；缺跨机重新匹配向导、统一适配版本检查、GUI 更新/回滚中心。GUI 导出方案仅包含高级中继设计。依据：`app_routes.py`、`store.py`、`runtime.py`、`tools/build_windows.ps1`、`tools/smoke_exe.py`、[打包说明](Windows打包.md)。

**完成标准：** 改变用户名、盘符、程序位置和端口的第二环境仍能恢复连接意图；无适配、旧后台、旧数据或更新失败时可理解且不丢原设置。源码、独立 EXE、中文/空格路径分别验收。

### F10 · 一致、易懂且可继续操作的交互

**用户目标：** 不需要学习网络术语，就能找到入口、理解每一步是否生效，遇到失败知道如何继续。

**通用行为：** 主流程以软件和任务为起点，画布支持点击/键盘/拖放；规则显示具体网站、范围和去向。配置保存、入口可用、应用采用和业务结果分别显示。所有未知/失败/不支持状态都有说明和可执行下一步，快捷入口保持同样含义。

**现状：四步流程已实现，跨机与完整业务验收未完成。** 添加、工具拖放、具体规则和状态分层保留；软件属性已统一为检查、诊断、应用、验证。诊断地址留空确实可执行，建议只入草稿、预览可取消、失败反馈有下一步，选择对象/连线/地址变化不会把异步旧结果显示为当前结果。合成事件测试与隔离浏览器点击验收已通过；真实新电脑、所有窗口尺寸/拖放及真实业务验收不能由此替代。依据：`web/app.js`、`web/routing-view.js`、`tools/test_app_flow_ui.js`。

**完成标准：** 用户无需知道软件适配细节就能完成通用任务；未知软件、屏外节点、小窗口、检测失败、待保存和后台失联均可理解并继续处理。界面视觉与实际交互验收不能由合成 DOM 测试代替。

表中未带目录的 Python 文件均位于 `proxyworkbench/`。

## 按通用能力安排后续工作

以下保留通用能力的实施方向，不表示全部已排期。0.6.0 已在既有范围贯通“流程”阶段；其他完全未实现能力暂缓，应用实例只作为每项工作的验收输入。

| 建议阶段 | 能力与交付范围 | 不应退化成的实现 |
| --- | --- | --- |
| 基础 | F01/F02/F06：统一能力、身份、配置和日志来源；允许手动补充 | 只加一个软件名、一个端口或一个日志目录 |
| 流程（本轮已有范围已贯通） | F04/F05/F10：画布内检查、解释、预览、应用、复测，GUI/快捷方式共享应用检查；后续按实际适配补覆盖 | 为每个案例另设一个“一键修复”按钮 |
| 观察（暂缓） | F07：活动/健康证据、停滞分类、恢复评估；复用前两阶段 | 某个后台出错就循环重启 |
| 独立扩展（暂缓） | F03/F08：扩展接入方式及请求分析；按协议和能力声明范围 | 接上某个引擎就宣称全部软件/协议可用，或把活动列表改名为抓包 |
| 复用 | F09：迁移本机绑定、兼容性检查和恢复；F10 随每阶段验收 | 拷贝旧机器端口和路径，或以开发机成功代表普遍可用 |

通用能力至少应覆盖不同结构的两类应用样例或独立隔离样例，并包含一个未知/不支持对象和一个相似症状但不同原因的反例。样例不必操作用户生产应用；发布时分别记录隔离验收与真实业务验收。具体适配可单独交付，但只能标成“该适配已支持”，不能因此关闭整项通用需求。

## 实现与验证记录

### 2026-11-08：0.6.0 共享流程实现验收

需求重整之后，本轮完成内置应用适配、共享应用检查、画布四步流程与验证/用户反馈分离。实现与成品分别完成以下检查：
